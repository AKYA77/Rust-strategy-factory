# Standalone research loop

The Rust process runs without Codex or an LLM. Current scope is training research with one bounded worker and one in-flight task. It does not issue independently validated qualifications. Default candle screening rejects proven absence of signals. Optional exact fixed-market proof screening can also reject mathematically impossible entries with deterministic tick audits. Signaled receipts now include bounded hypothetical USD M1 cash estimates and conservative shadow-policy comparisons with actual ticks; uncertainty/unsupported/partial cases stay explicit. Unproven and approximate-shadow candidates always run ticks; proof-only skips are separately labeled. See [candidate screening](candidate-screening.md) for assumptions, limits and remaining policy work.

Build with `cargo build --locked --release`. For a synthetic development exercise, from the repository root:

```sh
mkdir -p state
cargo run --locked -- fixture EURUSD state/fixture.json
cargo run --locked -- research config/research.example.json state/research.sqlite 10
```

The optional final number is a completed-step budget. Omit it to keep researching until stopped or the configured search budget is exhausted. The first output line is compact JSON containing `run_id`; final output is a persisted status. Paths inside the configuration resolve relative to the configuration file. No files are overwritten by `fixture`. These are short artificial 2025/2026 windows, not real coverage or a full 24-month dataset.

Use actual verified normalized datasets for real training research. Non-USD quote inputs require an explicit event-aligned conversion JSON file, referenced as `"conversions":"path.json"` alongside `dataset`. Future/stale/missing rates are rejected; no rate is inferred. Source/profile/complete-history approval and independent scientific evaluation remain mandatory before any qualification.

Control a running coordinator from another terminal, substituting its actual printed ID:

```sh
cargo run --locked -- research-status state/research.sqlite RUN_ID
cargo run --locked -- research-control state/research.sqlite RUN_ID paused
cargo run --locked -- research-control state/research.sqlite RUN_ID running
cargo run --locked -- research-control state/research.sqlite RUN_ID stopped
```

Pause/stop apply after the current safe task. Paused coordinators wait with lease heartbeats. A stopped run exits; set it back to `running` before restarting it. A finite step budget releases the coordinator lease without resetting its desired control state or cursor. Restart with the same binary, inputs and configuration to continue its cursor. A crashed coordinator or experiment can be reclaimed after its lease expires; a stale worker cannot advance the cursor. A result committed just before a crash is reused rather than simulated again. The compiled compute-source/compiler/target/profile/dependency digest participates in experiment/run identity. Embedded UI-only changes preserve it; changed computation or build profile establishes a new execution revision. Keep one build profile/revision for a frozen validation protocol.

Each input gets one candidate in round-robin order. Frozen base templates expand into deterministic new parameter/entry regions. `max_regions` is a deliberate campaign budget; exhaustion stops with the cursor intact rather than endlessly generating invalid duplicates. Counters distinguish newly completed tick simulations, rejected zero-signal/proven-no-entry screens, cached results and failures. They do not claim full-history evaluation or qualification. Permanent step records retain failures and cursor outcomes.

Limits: at most eight inputs, configured total event budget up to two million, 128 MiB total JSON input files at CLI load, one worker/one active task, at most four million retained feature cells, bounded grammar and result metadata. The state-file budget covers the SQLite file/WAL/shared-memory files and pauses before another task when headroom is low. It is backpressure, not a filesystem hard quota; one task may change file sizes before the next check. No scientific evidence is deleted to recover space. Increase capacity or archive/restore through a reviewed operator procedure; do not remove committed evidence or reset experiment identities.

Large native history, large immutable result artifacts, dynamic worker pools/supervision, OS-enforced CPU/RSS quotas and comprehensive crash/disk-full/VPS acceptance remain unfinished. Current oversized result publication is recorded as failure, never described as a completed backtest. Use `backup` and `registry-check` to create and verify an online backup; only start a restored coordinator when old processes are stopped and stale leases have expired. Other application services are unaffected.

Optional `limits.training_window` is an object with `start_ms` and `end_exclusive_ms`. Real-data autonomous runs require it; synthetic software tests may omit it. Prior candles only warm indicators. Each evaluation starts flat at $20, excludes earlier signals, and consumes no quote at or beyond the exclusive end. Still-open positions/pending orders remain unresolved, with no invented boundary fill. This is the execution foundation for independent protocols, not a completed scientific validation/approval workflow.

Optional `limits.improvement_children` enables durable training improvement jobs (default0, maximum4). Each completed or proven-no-signals base checkpoint atomically schedules one job. The next checkpoint drains it before another base candidate, preserving at most one queued job and bounded depth: children do not schedule descendants. Only the current compiled revision can enable this mode. Explicit training authorization and exact-context review checks still apply. A job records diagnosis/review identities or its failure; `improvement-jobs <registry.sqlite> <run-id>` reads the latest100 records, with complete history retained in backups.

Base counters (`executed`, `rejected`, `reused`, `failed`) continue to describe base-candidate checkpoints. Separate improvement counters describe queued/completed/failed jobs and child receipt links. Receipt links can reference cached/shared experiments and are not new simulation counts; registry experiment/lease counts remain authoritative. A completed job may have no child proposals when its evidence is unresolved. The dashboard labels these scopes explicitly. The CLI step budget counts base or improvement checkpoints, so the base cursor can stay unchanged while a job completes.

A pending job survives pause/stop/restart and coordinator fencing. Evidence committed before its job checkpoint is reused. State pressure pauses with its queued job intact; other job errors remain permanent failed records. Improvement checkpoints commit at most one missing experiment. Subsequent checkpoints reuse earlier receipts; a final checkpoint publishes the complete review. Pause/stop and coordinator renewal occur between children. A single running experiment must still reach its safe completion boundary. No OOS/final adaptation, qualification, OS hard quota or unattended process supervisor is supplied by this feature.

On Unix, SIGINT and SIGTERM now request a graceful process exit at the existing experiment checkpoint boundary. Listeners are installed before the coordinator ready line. After the current step, the coordinator releases its lease and prints final status; desired running/paused state is preserved, so the same binary/config can restart immediately. A paused process also exits promptly. These signals do not preempt a replay or change its financial outcomes. SIGKILL/OOM/hard service timeouts and crashes still rely on committed receipts/fencing/lease expiry. Process acceptance tests cover both signals in both running/paused state, no leftover claimed experiment and immediate same-run restart.

Optional `limits.shadow_policy` selects versioned candle shadow diagnostics (see `config/research.example.json` and the candidate-screening runbook). Changed thresholds/seeds get distinct campaign/experiment identities; comparable training reviews preserve the parent selection. Approximate shadow failures always run ticks. Optional `limits.proof_policy` can skip only exact fixed-market impossibility proofs, with mandatory deterministic audit sampling and fail-closed contradiction handling; see `config/research-proof.example.json`.

`limits.indexed_policy` is currently supported by the explicit training batch/API and comparable reviews, with reference audits and failure blocking. The autonomous `research` command refuses it until a checkpoint-aware shared-index lifecycle exists; ordinary default operation stays sequential.

### Registered synthetic corpus recovery

`corpus-step SPEC_JSON STRATEGY_JSON REGISTRY MAX_CANDLES FEATURE_CELLS MAX_RECEIPTS NEW_CHUNKS LEASE_MS` executes a bounded step against a frozen registered identity. `NEW_CHUNKS` is 1–64 and the lease is 1–86400000 milliseconds. Repeated invocations resume committed account checkpoints, yield pending leases, and reuse verified completed receipts. A failed terminal result stays failed. The current implementation revalidates source artifacts and recomputes the saved prefix before advancing; it provides recovery semantics without a fast-seek throughput claim.

Use `corpus-status REGISTRY EXPERIMENT_ID` to inspect verified cursor/control metadata. `corpus-control REGISTRY EXPERIMENT_ID paused` prevents new claims and final publication; `running` resumes a paused job. `stopped` is irreversible for that identity. Existing in-flight work remains subject to lease and publication fencing. A registry backup preserves checkpoints and controls, but does not package the source corpus artifacts: restore those verified artifacts separately. Recovery tests cover a killed process waiting for a database writer and independent continuation of a paused backup. Power-loss and disk-full acceptance remain unfinished.

This path accepts synthetic training corpora with literal USD conversion only. Real, protected and unsupported conversion contexts are refused. Synthetic receipts cannot qualify a strategy.

`corpus-batch CONFIG_JSON REGISTRY MAX_ROUNDS` runs 1–10000 bounded checkpoint rounds. The config is at most 1 MiB and contains `specification` (relative to the config), `strategies` (1–256 unique strategies), `budget` (the per-job candle/feature/receipt caps), and `limits`. Limits require `workers` (1–16), `max_parallel_candles`, `max_parallel_feature_cells`, `max_parallel_receipts`, `max_new_chunks`, and `lease_ms`. Concurrent caps must cover the largest budgets for the requested active workers. Each worker owns its registry connection; completed outcomes remain in input order.

A session returns its round count, stop reason and final per-job results. It stops on completion, job errors, a round limit or when every remaining job is held/busy/terminal. This avoids spinning against paused jobs or active leases. SIGINT/SIGTERM stop after the current bounded round; restart the same command to resume. No work is scheduled after the process exits. Object-count caps do not establish operating-system CPU/RSS enforcement, optimal worker count or representative throughput.

Optional corpus-batch `resource_guard` contains positive `maximum_process_rss_bytes` and `minimum_host_available_memory_bytes` (zero disables the host reserve threshold). Before each bounded round the Linux operator process checks its RSS and host MemAvailable. At/above the RSS threshold or below the host reserve, the session returns `resource-pressure` without starting another round. The admission observation/reasons are included in its output. Observation failure refuses execution. Change the operator policy and restart the same frozen jobs to resume. `resource-status` prints a fresh bounded observation and available parallelism.

This admission guard samples round boundaries. It does not constrain transient allocations inside a round, CPU use or disk space. Host available memory is not a cgroup allocation. Keep worker/object caps and externally enforced service CPU/memory limits; choose thresholds below those hard limits with measured headroom. Hard OS/cgroup enforcement and integrated autonomous search pools remain unfinished acceptance work.

### Generated native corpus research

`corpus-search CONFIG_JSON REGISTRY MAX_ROUNDS` generates and freezes candidates, drains each admitted batch through existing bounded workers, and replenishes the next deterministic slots until the declared candidate budget is exhausted. Config fields are `specification`, `seed`, `maximum_candidates` (1–4096), `queue_width` (1–32), `budget`, `limits`, and optional `resource_guard`. Budget/limits/guard have the same meanings as corpus-batch; strategies are generated rather than supplied. Config bytes are capped at1 MiB. The specification path is relative to the config.

`corpus-search-status REGISTRY SEARCH_ID` inspects verified cursor/slot metadata without requiring source artifacts. `corpus-search-control REGISTRY SEARCH_ID running|paused|stopped` changes durable controls. Resume requires an operator process; stopped/exhausted searches cannot be reopened through control. Execution errors pause the search and remain error slots. Current resume can continue subsequent candidates; explicit bounded retry/history is the next unfinished feature.

A session returns its bounded round count, stop reason and final search snapshot. It stops rather than spinning on held/busy work, and SIGINT/SIGTERM exit after the current safe round. No work remains running after the process exits. The source/generator/build identity is frozen: use the original build/artifacts to continue an old identity after a compute change. Back up source artifacts separately; registry snapshots preserve queue/checkpoint metadata. Generated slots, completed slots and canonical cache hits are separate from new immutable tick simulations. Synthetic search cannot qualify a strategy.

`corpus-search-requeue REGISTRY SEARCH_ID MAXIMUM_SLOTS` explicitly requeues eligible execution-error slots under their existing keys. Require paused state, no active coordinator lease and free frozen queue capacity. A request is1–32 slots, with at most three requeues per slot. The command/API resumes durable control state but starts no worker. Child leases and committed results remain immutable; an active child can cause held-or-busy until it yields/expires. The same build/source/configuration is still required for execution.

Status snapshots include exact requeue counts, eligible slots/capacity and recent stored prior-error records. Requeue events are not new financial trials or new strategies. Deterministic budget/source failures are not repaired by retry; changing frozen execution inputs requires a new search identity. See [bounded history policy](../DECISIONS/0011-bounded-error-requeue.md).

## Multi-corpus bounded sessions

Prepare one existing `corpus-search` JSON operator configuration per synthetic USD input. Register an ordered fleet configuration, for example:

```json
{"sources":[{"name":"EURUSD fixture","config":"eur-search.json"},{"name":"Gold fixture","config":"gold-search.json"}],"coordinator_lease_ms":60000}
```

Paths resolve relative to the fleet file and are stored canonically. Run `corpus-fleet-init fleet.json registry.sqlite`, retain its fleet ID, then `corpus-fleet registry.sqlite ID 100` for at most100 bounded input visits. Use `corpus-fleet-status registry.sqlite ID` to inspect the persisted next input and latest obstacles. No process runs after the command exits. SIGINT/SIGTERM requests exit at a visit boundary; filesystem stalls and OS enforcement are separate limits.

A missing or identity-changed source blocks only that input. Restore original source/configuration before resuming; do not edit financial parameters to bypass the frozen identity. One no-progress cycle pauses rotation. Inspect child search state and explicitly requeue eligible errors through the existing bounded mechanism when necessary, then `corpus-fleet-control registry.sqlite ID running`. Parent pause/stop controls do not reset or stop independent child leases. Permanent stop and all-budget exhaustion cannot be resumed. Dashboard input-rotation controls start no workers; exact snapshots redact local references/tokens. See DECISIONS/0012-multi-corpus-rotation.md for quotas and acceptance limits.

Optional disk admission: add `"disk_guard":{"minimum_available_bytes":1073741824}` to a corpus batch/search operator configuration to require at least1 GiB available before a new bounded round. `disk-status registry.sqlite` reports exact current observations without creating a new registry. A `disk-pressure` exit preserves progress and starts no extra round. Adjusting this operational source threshold preserves frozen child research identities. Missing/unsupported observations fail; omit the optional guard to disable this admission policy explicitly.

A fleet can freeze the same global policy during `corpus-fleet-init`; it refuses before claiming a coordinator or advancing visits under pressure. Global policy changes require a different parent fleet. Per-source policy remains adjustable in the referenced search file. A held source does not prevent another ready input from progressing; explicitly resume a no-ready-paused fleet after restoring conditions. Dashboard filesystem cards and exact fleet reserve display are read-only observations, not hard disk guarantees. See DECISIONS/0014-disk-admission.md for staging/link headroom and limits.

Schema11 search controls expose pause origin, a state epoch and bounded transition detail. `operator` means explicit operator intent; `worker_error` means the worker returned an error, which may be permanent; `legacy_unknown` means no reliable old origin exists. None of these currently enables automatic retries. Explicit requeue still requires paused/inactive state and existing capacity/per-slot budgets. Read/export status to preserve original error evidence before acting.

Transition detail is complete only since tracking began and only while `history_complete` is true. At128 per-search or4096/8 MiB global detail, the verified head keeps an explicit omitted count; stop is not blocked by that logging capacity. Before upgrade, stop older foreground/dashboard processes and keep a verified snapshot plus matching binary for unfinished old-build work. Migration revokes old coordinator tokens and preserves frozen keys; it cannot retune a search to a new compute revision. See DECISIONS/0016-durable-search-control.md.

Schema12 error snapshots distinguish registry_admission_busy, unclassified, worker_interrupted and legacy_unknown. Only a directly observed SQLite busy/locked admission code is a retry candidate. Read the current pause origin and state epoch as well: no automatic policy is enabled yet, and a typed candidate does not authorize overriding an operator pause. Human strings such as “database is locked” are not classified by text. Manual requeue keeps the old kind/error in immutable history and retains all existing lifetime/capacity limits.

Worker-start admission failures now return a bounded pool report with zero started workers and aligned job failures; inspect failure counts/jobs rather than treating any returned report as successful completion. Before schema12 upgrade, stop old processes and keep a verified snapshot plus matching binary. Migration preserves frozen keys/job bodies and labels old errors unknown. See DECISIONS/0017-typed-worker-failures.md.

Configure an immutable policy with `corpus-retry-configure registry.sqlite SEARCH_ID policy.json`, using e.g. `{"backoff_ms":1000,"maximum_slots":1}`. Inspect `corpus-search-status` for the exact control epoch, then `corpus-retry-admit registry.sqlite SEARCH_ID EPOCH`. A held/backoff response performs no requeue; a requeued response still starts no worker. Preserve its raw self-attributed decision receipt. Source classification, operator intent, deadlines, child leases and lifetime/history caps continue to apply.

The authenticated dashboard exposes the same bounded freeze/check actions and exact decision download. It cannot retune a frozen policy or launch workers. Use the current epoch after every effective state transition; stale requests hold. No browser timestamp is accepted. Foreground scheduling and durable decision/session history remain next requirements.

Foreground supervision records durable invocation observations. Use `corpus-supervision-sessions DB`, `corpus-supervision-status DB SESSION_ID` and `corpus-supervision-stop DB SESSION_ID`. A stop request is cooperative at a safe checkpoint; it does not stop the generated source permanently. An unclosed record is not proof that its recorded PID is live: inspect the process you actually own. Restart produces another identity and retains prior evidence. At128 retained sessions further foreground admission refuses; preserve the registry/backup rather than deleting records. Status exports omit owner tokens; raw registries remain private operational state.
