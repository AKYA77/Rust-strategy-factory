# Durable bounded multi-corpus rotation

A fleet freezes an ordered list of one to eight independently identified synthetic USD searches. Registration verifies every input and stores canonical local operator-config references plus frozen search identities; it starts no workers. Financial parameters, source bytes, candidate generator, budgets and compute revision stay bound to each search. Worker-count tuning remains operational. Changed identities are refused per input.

Each visit executes at most one existing bounded search round, then atomically publishes the next input cursor and exact counters behind a separate token/attempt/expiry fence. Shared coordinator fencing serves both searches and fleets; child experiment leases remain independent. A committed child result survives a lost fleet publication and is reused after restart. Visits and observed-progress counters are not new simulations. Rotation is round robin by bounded rounds, not equal CPU allocation or a production throughput claim.

Returned source/configuration errors are bounded and isolated so another input can progress. The latest obstacle remains attributed to its original source visit after restoration. One complete cycle without progress auto-pauses; explicit resume resets the idle counter. Exhaustion means all declared child candidate budgets are exhausted, not that the blueprint or research space is complete. Stop and exhaustion are irreversible for this fleet. Fleet controls affect future rotation and fence publication, without stopping independent child processes or launching workers from the browser.

Configuration bodies are limited to64 KiB, inventories to16 fleets, names to64 bytes and errors to512 characters. Existing actual-read1 MiB operator-file limits and per-search/pool quotas still apply. Optional global and input resource guards prevent new work at admission boundaries. These are not hard OS controls, filesystem-stall deadlines, or full historical error journals. Immutable configuration/reference triggers, validated counters, integrity checks and verified backups cover local persistence; external owners can rewrite a database.

CLI: `corpus-fleet-init CONFIG DB`, `corpus-fleet DB ID MAX_VISITS`, `corpus-fleet-status DB ID`, and `corpus-fleet-control DB ID running|paused|stopped`. The runner exits on bounded visit budget, signal, resource pressure, held/busy state, no-ready cycle or exhaustion. Restart requires an actual process invocation. Config example and operator steps are in the research-loop runbook. Authenticated status/control/export use existing CSRF/origin/session enforcement; snapshots redact paths and tokens.

Synthetic EURUSD and XAUUSD tests cover alternating visits, persisted cursor across processes, full scalar receipt equality, blocked/restored input isolation, backup continuation, worker-only tuning versus identity changes, coordinator replacement/control fencing, child-before-parent publication recovery, resource admission and corruption refusal. The browser suite exercises the actual service/database on desktop/mobile and restart. Real/protected/non-USD replay, scientific qualification, process supervision, hard resource enforcement and representative performance acceptance remain unfinished.
