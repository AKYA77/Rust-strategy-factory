# File-backed permanent result receipts

Schema10 adds immutable per-experiment artifact references. New serialized receipts up to256 KiB stay inline. Larger receipts, up to64 MiB, are stored in `DATABASE.artifacts/HASH.json` beside the canonical database file. The hash remains BLAKE3 of the original canonical JSON receipt. Public result/reuse/export values are unchanged. Legacy inline receipts remain readable without rewriting their bytes or identities during migration. Older binaries must refuse schema10; a binary rollback does not downgrade a registry.

Completion uses an immediate registry transaction, checks outcome-specific controls and current token/attempt/expiry, then writes a random create-new staging file, syncs it, links the content-addressed destination without replacement and syncs the directory. The compact summary and immutable reference commit with the terminal experiment/event. Concurrent duplicate completions have one winner. A database failure after file publication leaves unreferenced permanent evidence; retry verifies and reuses those bytes. Existing mismatched files and symlinks refuse without overwriting them. Stale workers do not create files. Local owners can still rewrite external files/database; this is application integrity, not independent evidence authentication.

Readers enforce regular-file type, exact declared/actual length and a64 MiB actual-read bound, validate file hash, parse JSON and compare its derived compact summary/reference before returning the original receipt. Missing/corrupt/reference-mismatched artifacts fail closed, including cached result reuse and duplicate completion. Small history summaries retain bounded strategy/manifest context, realized equity and actual trade count; full details and exact exports use the verified receipt. The full bounded receipt is still materialized before trade paging; this is not constant-memory streaming or a completed full-history artifact format.

Per store,4096 physical files and1 GiB count referenced, unreferenced and partial files. Admission is serialized by the registry writer. Unknown entries, symlinks, oversized files or exceeded caps refuse. Publication admission now reserves both staging/final link entries and twice the file length for its temporary two-link window; inventory byte counts are summed file lengths, not allocated blocks. See0014-disk-admission.md. No automatic deletion or pruning occurs: genuine completed/rejected/failed evidence is permanent, and uncommitted residue is retained for operator inspection. These are application admission limits, not OS disk quotas. Checkpoint row/body budgets remain separate; external result storage does not remove checkpoint or replay budgets. In-memory registries cannot publish external receipts.

Native online backups first freeze a SQLite snapshot, then copy exactly its referenced immutable files into a new destination store and verify the resulting registry. The store destination must be new. Native failure may leave an incomplete new backup that must not be activated. The operations wrapper verifies in private staging, publishes synced artifact links first and publishes the database without replacing a path last. Offline restore copies bounded files into staging, migrates/verifies only that copy and preserves the source. A crash between artifact and database publication can retain an unreferenced destination store; never delete it automatically or claim atomic publication across both objects. Copy/move the database together with its renamed `.artifacts` sibling. Never move only SQLite state when file-backed receipts exist.

`registry-artifacts DB` and authenticated `/api/artifacts` expose exact metadata/physical counts without paths, writes, deletion or a false content-verification claim. `registry-check DB` verifies all referenced receipt content. Dashboard storage cards distinguish physical evidence bytes/partial files from indexed receipts. The operations and browser suites use actual synthetic replay receipts, not submitted performance metrics. Synthetic data never qualifies.

Tests cover large receipts beyond the previous8 MiB limit, canonical identity/full-u64 preservation, idempotence, concurrent completion, immutable index, backup/renamed relocation independent of original files, corrupt/missing files/summary mismatch, failed/rejected retention, stale/forged leases before publication, quota pressure with sparse fixtures, symlink refusal, rollback after publication/retry without extra attempts, legacy migration and encoded serialization bounds. Specific rollback/crash-residue cases are covered; exhaustive power-loss/disk-full/production restore acceptance remains unfinished.
